# O2：兼容 exec v10 的编译优化

实施基线：main `1e0926d`。独立分支：`codex/compiler-o2`。
JIT 联合验收基线：`claude/runtime-performance-handoff-5mdt6h` 的 `93b5dd0`，
已通过 `585afbe` 吸收上述 main。O2 与该提交试合并无冲突；
运行时整合由 JIT 工作维护，O2 分支不修改运行时。

## 实施阶段

1. `-O2` / Java `Optimization.ADVANCED`、显式 O1 阶段集合、标量效果与 CFG 分析。
2. 跨分支传播、公共表达式复用、不可达分支和无副作用死赋值消除。
3. 有界标量内联，保留参数求值顺序和次数以及被内联运算的源码位置。
4. 整数范围证明驱动的安全循环不变量外提。
5. O0/O1 产物兼容、O2 双引擎/JIT 差分、性能与发行验收。

O0 仍为默认，O1 的阶段与顺序保持不变；O2 不选择后端、不改变 exec v10、
VM/JIT ABI、预算或原生编译阈值。跨优化级别允许错误调用栈缩短和资源耗尽位置变化，
保持普通错误类别与源码位置、getDepth、副作用和对象生命周期。
同一产物的 VM/JIT 观察仍严格比较。

新增分析只处理有界的封闭标量区域；未知宿主/反射/别名、对象清理及递归保守处理。
函数最多分析 4,096 个 exec 节点及 256 个参数/局部槽；超过时保留原有优化结果。
该限制控制编译器分析内存，与 LLVM 的 MIR 规模阈值无关。

## 当前实现边界

- O1 固定为原有四个阶段。O2 新增 `FLOW_PROPAGATION`、`CONTROL_FLOW`、`COMMON_SUBEXPRESSIONS`、`DEAD_CODE`、`SCALAR_INLINING`、`RANGE_LOOP_MOTION`，可由 Java 阶段集合独立选择。`--no-propagation` 同时关闭两种传播，其他关闭选项遵循语言说明。
- CFG、支配关系、活跃性和区间在编译器内部计算，采用确定性工作列表及循环区间扩宽。当前增强阶段要求整个函数及可达调用链为封闭标量代码；含对象、宿主、反射、未知调用或递归的函数保留 O1 结果。它不会把分析结论或新标记写入 ABD。
- 公共表达式复用使用局部槽中的已成功计算结果；覆盖直线代码、由它支配的条件分支及循环内未被改写的值。循环条件和循环体只沿用结果槽及全部操作数都不在循环写集合中的缓存，分支汇合保守清空；局部作用域结果不向外泄露。不会在首次执行前猜测有风险运算的结果。
- 死代码消除保留可能出错的计算和仍被赋值语句需要的声明。无引用、不会报错的标量初始化可删除；现阶段不压缩原有局部槽编号和 `local-count`，不会删除原函数及其 ID。
- 内联只处理完整初始化值、赋值右侧或返回值。候选最多 64 个 exec 节点、8 个参数，按冻结候选运行两轮，最多展开两层。实参一次求值并存入新槽，原函数局部槽重新编号。惰性表达式、循环条件及嵌套在其他运算中的调用不展开。
- 每个调用方新增槽最多 128；节点增长最多 `max(64, 原节点数 / 4)`。循环阶段复用已有槽，每函数最多移动 64 个初始化，不增加槽或节点。原节点与槽数按 O1 处理后的函数计量。超过限制或 ABD 嵌套限制时保留原代码。
- 循环外提使用循环头区间及整个循环的写集合，包括嵌套循环。只移动循环体直属、全函数仅一次写入、所有使用均在该循环内且被原声明支配的标量初始化；声明复用原槽。初始化必须在零次循环路径也确定安全、类型匹配，所有操作数不被循环修改。可依次移动相互依赖的只读初始化；跨迭代修改、作用域复用和可能报错的运算保留原位。不估算 MIR，也不改变 JIT 阈值。不展开循环、不缓存对象字段、不重排浮点表达式。

## 验收入口

统一普通与 sanitizer 验证包含 O2 定向差分和完整 VM 语料的 O0/O1/O2 对比。
`tests/compiler_o2_end_to_end.py` 可用 `--baseline-classpath` 检查旧 O0/O1 产物字节一致，
用 `--baseline-host` 验证旧 v10 运行库，用 `--jit-modes` 对同一 O2 产物严格重放。
模拟器可加 `--flow-batch-size 8`，将生成的 48 个控制流函数分为六批执行，
保留全部函数和独立参考结果；默认仍在一个样例中验证全部 48 个函数。
`tests/compiler_optimization_corpus.py --o2 --jit-modes ...` 对完整语料做同样的 JIT 对比；
编译模式必须记录实际进入次数，不能全部回退 VM 后算通过。
统一入口在含 JIT 的工作树中自动重放其可用模式，保留 JIT 分支已有的
`--jit` 构建、VM 预算差分和后端对齐流程。

性能入口 `tools/bench_compiler_o2.py --classpath ... --native ... --work build/o2-performance --modes off,on:3+llvm`
使用 Release 宿主、7 轮轮换顺序、每轮 5 批测量，并校验结果。
报告包含每轮编译耗时（包括 JVM 启动及文件写入）、ABD 大小、局部槽数、
冷启动与热态耗时，以及完整 JIT 会话统计。超过 5% 的热态回退列入 `regressions`，
需要独立复测；O2 新增原生规模拒绝直接导致验证失败。
测量时不得同时运行其他构建或测试，模拟器结果不作为硬件性能证据。

## 验证记录

接口及分析基础：30 项 exec 相关 Java 定向测试通过，包括原有 O1 回归、
等级/关闭选项、效果边界、循环收敛、分支汇合和整数区间。
这是阶段验证，不代表 O2 最终交付验收。

传播/CSE/DCE 阶段：35 项 Java 定向测试及 38 个脚本的 228 次树/VM 观察通过，4 项预算终止检查通过。保存的旧编译器对全部定向案例的 O0/O1 ABD 逐字节一致；此阶段由原有 v10 运行库执行。日志与报告位于 `build/o2-java.log`、`build/o2-stage2.json`。

增强内联阶段：40 项 Java 定向测试及 44 个脚本的 264 次树/VM 观察通过。错误调用栈允许缩短，但保留出错运算的原文件、行列；定向覆盖实参快照、重复参数、局部槽重编号、错误顺序、递归/观察者拒绝和两轮展开上限。报告：`build/o2-stage3.json`。

范围循环阶段：44 项 Java 定向测试及 48 个脚本的 288 次树/VM 观察通过，4 项预算终止检查通过。覆盖分支范围、位掩码范围、循环写入失效、零次循环和条件表达式中的潜在错误。全部定向案例 O0/O1 与原编译器逐字节一致，O2 使用实施前的 v10 运行库执行。报告：`build/o2-stage4.json`。

最终候选的定向兼容性：48 项 Java 测试、54 个脚本 / 376 次树与 VM 观察、
4 项预算终止检查通过，包含独立整数参考模型生成的 48 个控制流函数。
O0/O1 与保存的 `1e0926d` 编译器产物逐字节一致，O2 可由实施前的 v10 运行库执行。
回归发现并修复了循环条件错误复用回边上被修改的操作数或结果槽的问题；
旧候选会将应当发生的除零错误变成预算耗尽，修正后的候选保留原错误及源码位置。
报告：`build/o2-candidate2-compatibility.json`；复现记录：`build/o2-backedge-before.log`。
完整普通、sanitizer、JIT、AArch64 及最终性能和发行验证另行记录实际完成结果。

整合发行验收：运行库源码与 `93b5dd0` 相同，O2 编译器类内容与上述冻结候选一致。
`build/o2-distribution-final` 通过 33 项搬迁及消费者检查，包括 O2 源码/AST 字节一致、
最后一个优化选项生效、静态/动态 C++ 宿主和真实 JNI；191 项清单文件的大小与
SHA-256 全部吻合。日志：`build/o2-distribution-final.log`、
`build/o2-distribution-manifest-check.log`。

O2 定向回归另外在 1、7、31、63、64、65、127、255 的预算下重放六类优化产物，
逐项严格比较树、VM 及所选 JIT 模式。`probe` 仅测试调度边界，按运行时契约不产生
编译统计；其余模式要求统计存在且确实进入编译后的代码。

`93b5dd0` 联合版本的完整 O2 定向检查通过：54 个案例、936 次结果观察和
450 项预算检查，覆盖 `probe:7`、`eager`、`stress`、`on:2+interp`、
`eager+llvm`、`stress+llvm`、`on:3+llvm`。三个 LLVM 模式分别记录
616、101,676、128 次编译代码进入；无类型守卫违规或编译错误拒绝。
报告位于联合工作树的 `build/compiler-o2.json`。生成的 48 函数压力样例
在 LLVM `stress` 下需要超过常规单样例的编译时限，驱动只将该类样例的
执行等待上限扩大至 600 秒；实际结果与预算比较保持严格，性能验收另行执行。

完整普通验收：主分支运行库上 372 项 Java 测试、16/16 CTest（含真实 JNI）、
全部跨语言套件、463 案例 / 2,778 次 O0/O1/O2 观察、55,460 对树/VM 预算差分
和 1,376 次后端对齐均通过。日志：`build/o2-full.log`。

完整语料的联合检查已通过：`93b5dd0` 的七种 JIT 模式共 463 案例 / 6,019 次观察；
sanitizer 构建的四种可移植 MIR 模式共 463 案例 / 4,630 次观察。
LLVM 的 eager/stress/on 模式分别记录 1,009 / 27,650 / 470 次编译代码进入，
无类型守卫违规或编译错误拒绝。这些语料结果不替代另外执行的全量预算及后端对齐检查。

运行期间的环境中断及比较器修正采用保存证据后续跑：验证已完成前缀的源码、
编译器类摘要、源码/AST 产物以及原始树/VM 观察，再对剩余案例执行原驱动。
完整报告的 `segments` 字段指向保留的前缀与新执行的尾部。比较器修正只移除
跨优化级别观察中宿主事件内嵌的预算余额；原来仅移除顶层余额会误报两步的差异。
普通错误、副作用及同一产物的树/VM/JIT 比较规则不变，原始失败报告保留。

AArch64 模拟验证：18/18 CTest、59 个定向案例 / 1,046 次观察 / 450 项预算检查、
463 个完整语料案例 / 6,019 次观察全部通过，包含七种 JIT 模式。LLVM 模式的
进入次数及编译函数数与 x86_64 语料相同。这是 QEMU 功能验证，不是硬件性能证据。
报告：`build/o2-aarch64.json`、`build/o2-aarch64-corpus/report.json`。

完整 JIT 后端对齐发现 `93b5dd0` 的 LLVM stress 既有问题，已用旧编译器 O0
产物独立复现，不能宣告联合验收全过。最小程序、回溯、另一个独立等待超时及
修复责任边界见 [JIT 基线验收阻塞](JIT-93b5dd0-validation.md)。O2 运行时文件保持不变。

性能门槛调整：候选 2 的 `range_loop` 在首轮 7 × 5 测量中 VM 耗时比为 0.801，
LLVM 为 1.232；独立复测（同样 7 × 5、每批目标 0.25 秒）分别为 0.807 / 1.275。
因此收紧新建循环临时槽的收益判断，保留原 `range_loop` 作为便宜表达式回归组，
并增加 `range_division` 验证较高成本的安全外提。首次测量和复测保留于
`build/o2-performance-final/report.json`、`build/o2-performance-repeat-range/report.json`，
不能将这两个报告当作调整后版本的性能验收。调整后的全部 373 项 Java 测试及
ABD Java 回归通过；新的原生、JIT 及性能结果另行记录。

候选 3 的成本门槛仍未解决问题：`range_division` 的 VM 耗时比为 0.671，LLVM 为 1.225。
因此最终收紧为移动已有只读局部变量的初始化，复用原槽，停止新增循环临时槽。
候选 4 的全部 374 项 Java 测试与 ABD 回归通过；三种循环的独立 7 × 5 测量通过，
保留前两种原始负载作为回归组，新加 `range_local` 验证实际发生的外提，
其 VM / LLVM 耗时比分别为 0.575 / 0.532。原始失败报告及新报告保留在
`build/o2-candidate3-loop-performance/report.json`、`build/o2-candidate4-loop-performance/report.json`。
完整性能与最终产物复核另行记录，不能用这三个定向样例宣告整体加速。
