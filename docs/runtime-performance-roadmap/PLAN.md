## 2. 现在确定的架构决策

### 执行表示

第一阶段保留 exec v10 和 JNI snapshot v10。内部使用独立的 `ExecutableProgram`，含连续指令、常量池、函数记录、已解析上下文、调用目标及 PC 到源码位置/逻辑预算点的映射。外部文件格式不是内部 VM 数据结构。

采用寄存器执行器和显式帧。局部变量本来已用数字槽，本轮优化的是值表示、帧和指令执行；不会把“改成数字槽”当作新成果。最初使用可移植的 C++ switch 调度，不把 computed-goto、JIT 或平台专用汇编作为交付前提。

每个函数记录参数数、局部槽数、临时寄存器数、返回 ABI、泛型上下文数、模块 global offset/count、源码映射及清理描述。跳转与操作数在程序发布前验证，不能把非法寄存器、错误上下文索引或未知指令留给热循环处理。

### Value、Slot 与对象身份

- `Value` 内联 int32、uint64 address、float、double、bool 和 void；字符串、对象、buffer 使用明确的引用/句柄。ANY 表示类型检查规则，不充当新的实际值标签。
- `Slot` 是有身份的存储，包含值、声明/有效状态和所有权关联。未声明槽与已声明但值为 void 必须区分。
- `SlotId`、`FrameId`、`ScopeId` 是内部句柄。使用稳定槽区或分段池；不得让 vector 扩容使 owner、container、frame 引用失效。回收句柄必须防止内部旧引用误指向新槽。
- 脚本可见 address 位模式、偏移规则、父类字段前缀、first-fit 分配顺序保持。内部句柄不直接暴露为脚本 address，也不借本轮擅自扩大堆悬垂指针的语言保证。
- Value 的 C++ 拷贝不等于脚本对象赋值。类值复制、借用、临时对象移动、返回所有权转移由明确的运行时操作处理。

### 宿主接口

选择显式的 C++ API/ABI 迁移：先加入类型化访问器并迁移仓库中的宿主/JNI/插件，再移除对 `variable::value` 裸指针布局的依赖。不能同时维护一份旧 void* 存储和一份新 Value 缓存而忽略宿主裸写。

目标 API 区分值快照和可写槽引用；回调参数保持求值后的快照，宿主修改全局/堆槽通过指向同一真实存储的访问器生效。须明确保留的句柄在作用域结束、对象销毁及快照替换后的行为。原有公开裸字段访问需要迁移，不承诺旧宿主二进制兼容。

Java 高层方法签名和脚本语言语义保持；JNI 内部随新值/槽接口迁移。C++ 项目/API 版本独立更新，不机械修改源码 metadata、exec 或 snapshot 版本。所有静态/共享消费者及动态插件用同一套头文件重新构建；插件二进制改变后重新签名。

增加独立的运行时 ABI 握手，在调用插件注册/业务入口前拒绝不匹配的插件；签名仍在加载前验证。若签名封套需要携带 ABI 元数据，按其独立版本协调 signer、loader、工具和文档，不将其混同于 exec/snapshot 版本。

共享C++宿主也必须隔离ABI：同步运行库VERSION/SOVERSION或平台等价的链接身份、导出符号/ABI标识及CMake包兼容规则。消费者用错误头文件/运行库组合时须在链接、装载或显式握手处明确拒绝，不能等到布局错误产生未定义行为。插件握手不能替代这一检查。

### 调用、作用域与清理

`Frame` 保存函数索引、PC、槽区间、返回目的位置、模块全局范围、上下文、作用域/临时量水位和调试状态。`ScopeRecord` 保留逻辑作用域层级；`getDepth`、显式所有权提升及调用者/词法父环境区别不能因去掉 environment 对象而改变。

`CleanupAction` 和 continuation 显式表示析构、字段清理、临时量回收、返回转移、构造回滚及恢复控制流。return、break、continue、异常都携带清理目标水位。

析构、默认工厂、buffer 类元素初始化及用户比较函数会再次执行脚本。这些路径必须能暂停当前操作、压入脚本帧并恢复 continuation，最终不能在内部偷偷递归调用旧执行器。保留首个异常及其 trace；后续清理错误不能覆盖它。

嵌套对象复制、字段析构遍历和失败回滚也使用显式工作栈，不能仅改CALL而保留helper中的无界原生递归。预算耗尽时余额维持零，不赠送用户析构步骤；按现有行为尝试清理，脚本执行继续受预算限制，不执行脚本的必要存储释放仍完成。

登记所有权或发布新对象前预留对应清理记录；工作区不足时不能留下无清理责任的半成品。退栈及必要原生释放不得依赖新的无界内存分配。析构帧申请失败按既有首错规则处理，并继续完成可执行的存储回收。对象遍历优先保存节点/索引游标，不为全部字段一次性压入同阶数量的清理动作。

### 预算、错误与优化边界

- 初期精确保留旧执行器的逻辑扣费点，包括块、循环、调用、方法表条目和按对象/容量收费的路径。内部一个 opcode 不等于原来一步。
- 每个扣费点记录其源码位置和发生顺序。不能把副作用两侧的检查合并成函数入口一次扣费；融合指令也要能在相同位置耗尽预算。
- 保留脚本与宿主嵌套调用深度规则；普通脚本调用不再逐层增长 C++ 栈。原生栈上限继续约束实际原生栈，宿主/JNI 重入仍受保护。旧引擎因原生栈不足失败而新引擎成功，是单独标记的预期架构差异，不伪造旧失败。
- 为VM工作区引入独立的 `max_vm_workspace_bytes`，宿主可配置正值；不重新解释现有 `max_stack_bytes`。默认值先以64MiB为候选，R06记录Value/Slot/Frame/Scope实际大小及合法边界峰值，在R09接口定稿前固定通过布局门槛的默认值，不预先宣称64MiB足够。
- workspace按实际申请的backing capacity计费，包括寄存器、局部槽/索引、帧、作用域、临时量登记、cleanup/continuation、对象遍历和暂停重入工作区；同一执行会话的重入共享余额，不重新置零。只在空间增长时检查溢出及额度，不增加每条算术的检查。闲置池容量也受上限约束；这不是总RSS预算，不包含独立管理的代码/常量、宿主内存和对象/buffer payload。
- 新workspace上限及错误是可观察的资源契约，需增加C++配置、Java getter/setter和文档。测试合法最大槽头、末槽访问、多帧及回调累计、32k局部和大参数场景；不为单个fixture暗中放宽配置。它不替代对象堆、单函数槽数、step或逻辑调用深度限制。
- 优化不使用 `-ffast-math`。int32 溢出、地址溢出/下溢、浮点舍入、除零、短路、左右操作数快照及异常位置保持。
- v10 局部声明中的 declared_type 不能当作永久存储类型保证：当前加载器只验证编号，后续槽仍动态写入；global 类型不在 v10 中，宿主也能写槽。因此专用数值指令首先检查当前已求值操作数的 tag，失败转通用路径且不重新求值。只有已证明不可变的瞬时值可去掉检查。

## 4. 性能实验方案与采用门槛

基准位置拟为 `benchmarks/runtime/`、`tools/bench_runtime.py`、`tests/runtime_benchmark_host.cpp`；所有输入、二进制、日志和原始结果保存在 `build/runtime-perf/`。性能计时、分配计数、profiler 分三轮执行，避免 instrumentation 污染计时结果。

| 组 | 必测负载 | 要回答的问题 |
| --- | --- | --- |
| 标量 | int/float/double循环、比较、分支、位运算、短路 | 每次算术的分配/派发开销是否消失；checked数值语义是否保持 |
| 调用 | 空/短函数，0/1/4/16参数，普通递归、跨模块 | 每次调用的固定成本、槽复用和原生栈行为 |
| 对象 | 创建销毁、字段、类值复制/返回、自动/手动对象 | 扩容、稳定存储、复制和生命周期成本 |
| 虚调用 | direct、final、单一receiver、交替派生类、泛型派生类 | 派发自身与普通调用成本分别占多少 |
| 容器 | buffer标量/类元素、reserve、get/set、构造/析构 | view、复制与恢复状态机是否引入回退 |
| 边界控制 | C++、JNI、callback、load/flush、snapshot | 主线优化是否在边界或启动阶段转移成本 |

核心采用分数固定为四组各25%：标量循环/分支、普通调用、对象创建/字段/复制、虚调用。每组预登记的case等权，medium/large规模等权；small用于正确性和短调用成本观察。首次运行、加载、JNI、snapshot和字符串专项不混入核心稳态分数，但必须单独披露。具体迭代数在R01按旧基线校准并冻结；不能在看到候选结果后剔除慢项或改权重。

采样规则：固定编译器/优化参数和机器资源；旧新交错执行，至少7轮独立进程；每轮预热后测足够长批次，短用例目标计时窗口至少约250ms。编译、输入生成和I/O不在执行计时内；计时后必须检查结果。使用固定输入规模、max_steps/call-depth和随机seed；不能为候选单独放宽预算。

记录wall/CPU时间、吞吐、分配次数/字节、峰值RSS；平台允许时另采指令/分支/cache数据，缺失性能计数器不阻塞基本计时，但明确标注。报告中位数、离散范围和逐对比值；保留原始失败、超时和错误结果，不能把它们剔除为异常慢样本。

初始工程门槛（目标，不是已获得的结果）：

1. 语义与内存正确性是硬门槛。
2. R18默认交付要求核心稳态组出现可重复的整体改善；以几何平均至少1.25×为初始目标，并报告每一项，不能用几何平均遮住严重回退。R16仅确认候选功能闭合。达不到性能目标则定位profile和设计，不能只以测试通过宣告性能重构成功。
3. 单项连续两轮实验回退超过5%、峰值RSS上升超过10%时必须分析来源并修正，或在具体交付说明中给出明确、与目标相关的权衡。微秒级项目延长批次测量，不靠放宽阈值掩盖噪声。
4. 固定槽整数热循环在预热后，VM自身分配数不能随迭代次数增长。帧/槽池允许首次容量增长；外部调用、显式alloc和字符串构造单独计数。
5. R02以真实runtime的扩容/搬移计数和first-fit结果验收；既有容器探针数据只证明机制。
6. 新加载成本、编译耗时和RSS单独报告；生产切换后不能常驻旧执行树和新字节码两份表示。

## 5. 差分与语义验收矩阵

每个生成测试有固定seed、输入、预算、预期事件及超时。独立执行旧/新runner，比较返回标签和值、stdout、宿主事件、构造析构顺序、可见全局/堆状态、错误类别/消息、脚本trace和预算停止点。浮点按对应契约比较，负零用位模式/专用断言；不能以宽泛浮点容差隐藏算术变化。

对象内部生成ID可以在结构对照中受控规范化；用户提供address、地址算术结果和可观察first-fit分配不能任意规范化。旧实现不是唯一规范，差异按源码/语言/wire契约裁决，修复既有缺陷另加最小复现。所有预期差异按具体案例登记，禁止通用“忽略错误/地址/trace”开关。

关键矩阵：

- 左右表达式与参数求值顺序、RHS改变LHS、短路未执行分支、重复调用。
- return/break/continue跨多个作用域，getDepth、所有权提升和调用者关系。
- 正常析构、构造中途失败、析构再次失败、保留首个异常/Java throwable身份。
- 类值复制/移动/返回、借用、自动对象指针改写、buffer view在回调后失效。
- 泛型上下文、默认工厂、用户比较器、反射签名和对象结果检查。
- virtual构造/析构阶段换表、final/Base::、对象复制、非法receiver、恢复后的缓存。
- 对小型案例枚举预算1到完成所需点及相邻边界；比较每个失败点的副作用、trace和清理，不只比较最终成功结果。
- 真实小线程栈与JNI回调递归，逻辑调用深度和原生栈上限分开验证。
- VM工作区上限、暂停回调与重入累计占用、预算不足后首错/清理及宿主配置的边界/非法值；这类新增资源限制与旧引擎的预期差异单独登记。
- 双向snapshot v10、同序模块字节、损坏输入原子拒绝、恢复不析构旧状态/不重复onload。
- 手写v10 declared_type与实际值不同、宿主修改global/heap标签、typed fast path失配。

## 6. 构建、检查与证据管理

计划新增脚本尚未实现，不能把上面的拟定命令/文件视为已存在。现有完整验证入口为：

```sh
env -u JAVA_TOOL_OPTIONS python3 tools/build_and_test.py --offline
env -u JAVA_TOOL_OPTIONS python3 tools/build_and_test.py --offline --sanitize
env -u JAVA_TOOL_OPTIONS -u JDK_JAVA_OPTIONS -u _JAVA_OPTIONS \

```

普通与sanitizer共用 `build/java/`，必须顺序运行；sanitizer不包含真实JNI。先做每项定向测试，在可交付里程碑运行完整验证；同一源码已通过后，不因文档更新重复整套。公开接口/插件变动必须检查真实消费者，最终及运行时首轮交付执行发行搬迁。

新增benchmark的独立Release配置使用当前CMake入口；例如：

```sh
cmake -S . -B build/runtime-perf/release \
  -DCMAKE_BUILD_TYPE=Release -DAZSCRIPT_BUILD_JNI=ON -DBUILD_TESTING=ON
cmake --build build/runtime-perf/release --parallel 4
```

并行数按实际CPU/内存配额调整，旧新构建采用相同配置。Debug/sanitizer耗时不与Release混合；不通过删除检查、关断言或改用不同优化flag制造收益。

每个里程碑在 `build/runtime-perf/<编号>/` 保存命令、退出码、源代码SHA、工具版本、flags、输入摘要和原始结果。仓库文档只记录必要结论及可复现入口，构建产物不提交。更新路线图时分别标记“实现”“验证”“性能测量”“发行”，不能以完成其中一项代表全部完成。

## 7. 并行工作与集成顺序

可以并行：基准/差分工具、宿主特征测试、独立格式语料和文档；核心Value/Slot接口冻结后，字节码lowering与其测试可分开；运行时稳定后编译器IR可独立推进。

必须串行：Value公共接口落地→Slot身份→VM调用/清理→对象及泛型→宿主与snapshot→默认切换。`library.cpp`、`blocks.cpp`、`heepalloc.cpp`的所有权改造由同一集成人协调，避免多代理同时修改核心契约。普通/sanitizer/发行任务由单一执行者按顺序调度。
