# exec v11 设计：O3 与配套的格式、运行时和 JIT 更新

日期：2026-10-21（UTC）。开发分支：`exec_v11_main`。计划见 [PLAN.md](PLAN.md)，实际进度和验证证据见 [STATUS.md](STATUS.md)；三者冲突时以本设计为准并同步修订计划。

**用户确认的方向：** O3 及其需要的“更激进”优化放入下一个大版本 exec v11；O3 同时包含 (a) 扩大的内联与槽压缩、(b) 常量参数与泛型上下文专用化、(c) 对象标量替换、字段缓存与去虚化；彻底删除 `getDepth`；JIT 的原生规模上限随之调整。本轮不规划 v11 的全部 ABI，只纳入 O3 及其相关更新；v11 离正式发布尚远。

## 1. 动机

O2（[../compiler-optimization/O2.md](../compiler-optimization/O2.md)）在 15 组负载中只改变了 3 组的产物：`scalar_call`（内联，LLVM 耗时 0.335）、`range_local`（外提，约 0.54–0.57）、`repeated_expression`（公共表达式，约 0.91–0.95）；其余 12 组逐字节相同，对象组没有编译收益。限制来自四处：

1. **v10 没有“先执行语句再得到值”的表达式节点。** 内联只能放在语句根部（完整初始化值、赋值右侧、返回值）；嵌套在运算、惰性分支、循环条件中的调用都不能展开，否则改变求值次序或次数。`call_1/4/16` 的 `total + f(i)` 因此在 O1/O2 都不内联。
2. **`getDepth()` 让运行时作用域深度可观察。** 内联、合并作用域或删除对象作用域都会改变它，因此任何可达 `getDepth` 的函数都不能优化；它还迫使 VM 为标量帧中的内建调用伪造一条作用域链（`vm/host_bridge.cpp`，`invoke_external` 的 `lexical_depth`）。
3. **编译器生成的函数要么公开、要么成为对象帧。** `entry_kind=0` 的克隆可被反射和宿主按 ID 调用；`entry_kind=1` 会被 VM 归类为对象帧并传染所有静态调用者，失去 JIT 资格。
4. **所有算术都带溢出检查，虚调用没有守卫。** 范围已证明的整数运算仍要检查，JIT 中每个检查是一个退出点；跨模块可继承，因此非 final 虚调用无法静态解析。

JIT 方面：调用只有约 2 倍收益（`call_1` 每调用 2.70M 条指令，循环本身 285k），对象帧完全不进入原生代码；LLVM 编译时间随操作数和“恢复点 × slot”超线性增长，原生上限（2,048 个操作、8,192 个恢复单元）会让被内联放大的函数退回 VM。

## 2. 可观察契约

沿用 O2 的契约并作两处修改：

- **不变：** 同一产物在树、VM 和七种 JIT 模式之间逐字节一致（结果、异常类型与消息、trace、`remaining_steps`、回调次序、globals、堆、workspace）；不同优化档位之间保持返回值、类型、宿主副作用、浮点行为、普通错误类别和出错源码位置、对象构造/复制/析构次序。跨档位允许预算消耗与资源耗尽位置不同。
- **删除 `getDepth` 后：** 运行时作用域结构不再可观察，作用域只通过对象生命周期（析构次序、所有权转移）体现。优化可以自由增删、合并作用域，只要生命周期不变。
- **trace：** 不带 `-g` 时跨档位允许调用栈缩短（同 O2）。带 `-g` 时 O3 通过内联记录（第 4.5 节）还原被内联的帧，使 trace 的帧序列与源码位置和 O0 相同；专用化克隆以原函数的名称和位置显示。只有超出 64 帧上限后的省略计数可以不同。

## 3. 分支与版本策略

- 全部 v11 工作合入 `exec_v11_main`。每个阶段完成后合入该分支；阶段内可以改变 wire 格式、VM/JIT ABI 和快照内容，但**根结构中的 exec 版本号保持 10**，`EXEC_FORMAT_VERSION`、`ExecCodec.VERSION`、发行清单与相关测试样本暂不改。
- 由此 `exec_v11_main` 产生的、使用新构造的产物不能在 main 的 v10 运行库上执行，反之 main 的产物在 v11 分支上仍可执行（新构造只增不改，旧 opcode 语义不变）。这条单向兼容在开发期由测试保证：O0/O1/O2 的产物不使用新构造，`compiler_o2_end_to_end.py --baseline-host` 的旧运行库检查继续适用于这三个档位；O3 产物标记为仅限 v11。
- 正式发布时一次性把 exec 版本改为 11，协调全部读写端、版本检查、样本、文档和发行清单（第 9 节），并评估 JNI 快照版本是否随内容变化；之后合入 main。不保留 v10 兼容层。
- `getDepth` 删除是语言层的破坏性变化，同样只在 `exec_v11_main` 上进行。

## 4. 格式增补（exec v11 的 O3 部分）

只增加 O3 需要的构造；编号接在现有 0–53 之后，旧 opcode 不变。

### 4.1 表达式序列 `seq`（新 opcode）

`seq{statements:E[], value:E}`：依次执行语句，再求值并得到 `value`。它**不引入作用域**，自身不扣预算以外的工作量（与普通节点一样计一个 tick）。

- 序列中的语句只能对**已在外层声明**的局部赋值（SET/MOVE）或调用；不能声明（DEFINE）局部、不能 break/continue/return。被内联函数的局部和实参快照由编译器提升为调用者函数根块中的声明，序列内只写入。这样序列可以出现在循环条件、惰性分支和任意运算数位置而不引起“重复声明”或生命周期变化。
- 对象生命周期不进入序列：序列内不能创建拥有对象的临时值（编译期校验），这类调用仍按 O2 规则只在语句根部展开或不展开。
- 树执行器、VM lowering（依次 lower 语句再 lower 值）、校验和 JIT 分析都只需按普通表达式处理；VM 指令层面不新增指令。

### 4.2 私有函数（`entry_kind=2`）

编译器生成的克隆和专用版本使用新的入口类别 `entry_kind=2`（编译器私有）：

- 不能被反射、宿主、`call_virtual` 方法表或其他模块的 extern 找到；只有同一模块中编译器生成的直接调用可以调用它。运行时 flush 校验这一点。
- VM 按普通函数分类（不因 `entry_kind` 成为对象帧），JIT 可以编译它。
- ID 取自模块 namespace，从 `0xffff` 向下分配，跳过已占用位置；跨模块重复 ID 仍由 flush 拒绝。trace 和调试记录显示原函数名。

### 4.3 无检查整数运算

为 add、minus、multiply、shl 以及 increment 形态增加 int32 无检查版本（新 opcode）：两个操作数必须是 int（运行时仍检查类型标签，类型不符时与对应有检查运算同样报错），结果按二进制补码回绕，不报溢出。

- 编译器只在区间分析证明结果不溢出时发射；回绕语义只是为了在证明错误时各引擎仍逐字节一致，而不是可依赖的语言行为。O3 以外的档位从不发射。
- VM 中只省去 `checked_int` 分支；主要收益在 JIT：无检查运算没有失败退出，LLVM 中是普通 `add/sub/mul`，减少退出点和恢复单元，也让 LLVM 的循环优化可用。

### 4.4 方法绑定守卫 `guard_method`（新 opcode）

`guard_method{receiver:E, slot:int, function:int}` 得到 bool：当 receiver 是当前脚本的有效对象、其方法表有第 `slot` 项、且该项绑定 `function`（及与直接调用相同的上下文）时为真；**任何会让 `call_virtual` 报错的情况都返回假，不报错**。编译器把虚调用写成 `select(guard_method(...), 直接调用或内联体, call_virtual(...))`，失败路径保留原虚调用，因此错误、trace 和返回类型检查与原来相同。

- 读取路径同 `heap::methods_at`，但不抛出。函数 ID 随 namespace 重定位，在链接时参与引用遍历（`core/exec.cpp` 的 `reference_walk` 与树的引用表）。
- 守卫只在对象帧中出现（它读取堆）；JIT 在支持对象帧之前不处理它。

### 4.5 内联记录（调试信息）

每个函数的调试记录增加可选的 `inlined` 表：`[callee_name, callee_file, callee_line, callee_column, call_site_location]` 的列表，`locations` 中的每个位置可附带内联表下标（0 表示不在内联体中）。trace 在记录一个脚本帧时，先按链输出被内联的帧，再在调用点位置输出外层帧；64 帧上限同样适用。记录没有执行语义，不参与链接和重定位；不带 `-g` 时不生成。

## 5. 删除 `getDepth`

- **语言与编译器：** 从内建表（`Compiler.java` 的 `BUILTINS`）删除；`0x0abd0001` 永久保留、不再分配，调用、声明或 extern 该 ID 均报错。内建数量 20→19。
- **运行时：** 删除 `depth_function` 和 `ownership::depth`；内建表第 1 项保留为空槽，其余 ID 不重新编号（`core/ids.h` 的枚举与 `static_assert` 不变）。删除 VM 为它伪造的作用域链：`invoke_external` 不再需要 `lexical_depth`，标量帧的内建调用直接在基础环境上执行。
- **测试：** 所有权一致性语料中只观察深度数值的用例（`tests/conformance/scopes.py` 的 a12 系列中的纯深度部分、a12g、a12h，`assignment.py` 的 ce11/ce11b）删除；仍有析构次序或所有权含义的部分改为事件观察。`lifecycle_fuzz.py` 删除 `getDepth` 原子（生成摘要随之改变）；其他把 `0x0abd0001` 当作任意内建的测试改用别的内建；`conformance_mutants.py` 删除 `depth-counts-callers` 变异体。
- **文档：** README、LANGUAGE、QUICKSTART 及路线图中的说明同步修改；历史记录不改写。

## 6. O3 的组成

O3 = O2 的全部阶段 + 以下阶段。`Optimization.ADVANCED` 先改为显式的 O2 阶段集合（目前定义为“全部阶段”，新增阶段会自动混入 O2），O3 新增 `AGGRESSIVE`（CLI `-O3`）。每个阶段可由 Java 阶段集合和 `--no-*` 开关独立关闭。

### 6.1 (a) 内联与槽压缩

- **调用点：** 任意急切位置的调用，包括运算数、条件、循环条件和惰性分支，经 `seq` 原位展开；实参按原次序各求值一次写入提升的快照槽。
- **被调者：** 封闭标量区域中的任意非递归函数，可含 if/while/break/continue/多个 return（return 改写为写结果槽并跳出包裹块）；递归强连通分量只展开一层；调用链深度上限 4。
- **调用者：** 不再要求整个函数是封闭标量区域；调用者的其他部分可以含对象操作，只要被内联体本身是标量且调用点不在清理区域内。
- **槽压缩：** 最后运行；同类型、作用域不重叠（一个作用域退出后另一个才声明）的槽合并，保留 VM “已声明的槽不能再次声明”的规则；循环体每轮离开作用域，可以在轮内复用。降低 `local-count` 同时降低 JIT 的恢复单元。

### 6.2 (b) 专用化

- **常量参数：** 对某个调用点的常量实参（int/bool），以“被调者 + 常量实参向量”为键生成私有克隆；克隆以常量作为分析初值重新运行 O2/O3 阶段。每个被调者最多 4 个版本、每模块最多 64 个，只在克隆比原函数小（节点数减少至少 25%）或使内联成为可能时保留。
- **泛型上下文：** 按完整绑定上下文（不仅是 int/bool identity）生成私有版本，键包含全部上下文；版本数同样有上限（每个泛型函数 4 个）。

### 6.3 (c) 对象

- **逃逸分析：** 在 `ExecIr` 的结构化 CFG 上扩展 C06 的 `Escape` 摘要，补上 `OBJECT_ADDRESS`/`BLOCK_ADDRESS`（目前错误地归为 NONE）的流向；对象地址只作为 `mem_get`/MOVE 的常量偏移基址、或传给已被内联的方法时视为不逃逸。
- **标量替换：** 字面量对象和自动指针对象若工厂、构造、析构和全部方法调用都可内联、地址不逃逸，则字段改为局部槽，`new_block`/`#allocate`、`ob` 与 `ro` 消失；析构体在作用域的每个出口（正常、break、continue、return、错误）按原逆创建次序执行，错误出口沿用 `cleanup` 的 on-error 路径。按值复制的每个副本是独立的标量组和独立的析构调用。成员访问的存储和越界检查在编译期证明后省去。打印或比较地址、反射、宿主、`mem_send_up`、`od`、`check_object` 一律视为逃逸。
- **字段缓存：** 对未被标量替换但在区域内无别名的对象，连续的字段读取复用已读值；任何可能别名的 MOVE、脚本调用（可重入）、清理/drop/delete、宿主或反射调用及循环回边使缓存失效。缓存只复用已成功的读取，不提前触发错误。
- **去虚化：** 接收者在本函数内由已知类构造且未逃逸时直接调用（构造完成后方法表不再改变）；否则对本编译单元中没有可见覆盖的方法生成 `guard_method` 守卫的直接调用或内联体，失败路径保留 `call_virtual`。

### 6.4 无检查运算的发射

区间分析（`ExecScalarAnalysis` 的整数区间与循环扩宽）证明不溢出的 add/minus/multiply/shl 与自增改用 4.3 的无检查 opcode。只在 O3 中启用，可单独关闭。

### 6.5 统一代价模型

所有扩展阶段共用一个确定性的代价模型：节点增长、压缩后的槽数、ABD 嵌套、`ExecScalarAnalysis` 的 4,096 节点 / 256 槽分析上限，以及估算的 JIT 规模（VM 指令数与恢复单元，对照第 7 节的上限）。超出时回退到上一阶段的结果，不让函数因 O3 失去原生编译资格。

## 7. JIT 的配套更新

- **只写回活跃值：** 把每个退出点活跃的寄存器集合（运行时已计算 `exit_registers`）和新增的局部活跃性传给 LLVM 模块（ABI 新字段，布局摘要随之改变）；恢复块只装入允许的 slot，每个退出块只写回该点活跃的 slot，取消统一的 `leave` 写回。这消除“每个 slot 在每个块都活跃”导致的 phi 爆炸。
- **按规模选择流水线：** 超过阈值的函数使用 LLVM O1 流水线或快速寄存器分配，编译时间保持近似线性。
- **重新测量并提高上限：** 完成上两项后重新测量编译时间随操作数与恢复单元的增长，按“最坏情况约 1 秒”重新设定 `native_operation_limit` 与 `native_resume_limit`，并记录测量。
- **v11 构造：** 无检查运算在 MIR 中是不带失败退出的运算；`seq` 与私有函数对 JIT 透明（前者在 VM lowering 中消失，后者是普通函数）；`guard_method` 留给 JIT 支持对象帧的阶段。对象标量替换后的函数自然成为标量帧，进入 JIT。
- 后台编译不在本轮。

- **定向用例：** 每个阶段的正常行为与错误路径（嵌套调用的求值次序与错误顺序、惰性分支、循环条件、递归、专用化键冲突、对象各出口的析构次序、别名失效、守卫失败路径的错误）。

## 10. 风险

- 序列与提升声明会增加函数的槽和节点，O2 已测到新增临时槽让 LLVM 变慢（`range_loop` 1.23–1.28）；必须靠槽压缩和代价模型抵消，并由性能门槛把关。
- 对象标量替换触及所有权语义，是本轮风险最高的部分；只处理能完整证明的形态，其余保持原样。
- 去虚化的守卫依赖运行时方法表的读取语义；守卫必须在一切错误情形下返回假。
- 私有函数改变 flush 的可见性规则，需确认快照恢复、hint 重定位和跨模块重复 ID 检查。
- 开发期间 exec 版本号不变，v11 分支产物误用于 v10 运行库时报“未知 opcode”而非版本错误；这是有意接受的开发期代价，发布时消除。
